# StarHub × deepseek-harness 联动设计

> 日期: 2026-08-17 · 状态: **已按方案 B 实施(v0.81.0,2026-08-17)**——四方施工完成
> (dsh 插件 / Rust 主进程 / client-nav / Vue 面板),实施契约见
> `docs/联动实施-桥接契约-2026-08-17.md`;实施详情见 `CHANGELOG.md` v0.81.0。
> 起因: 用户提出「dsh 和 StarHub 这些工具无法联动」,并问「能否都收敛到以
> deepseek harness 为基础」。本文给出诊断、方案对比与推荐架构。
> 用户选定优先场景:**跨工具编排** + **一句话让 AI 打开并操作工具**。

---

## 1. 问题定义

「联动」不是指 AI 能不能调工具(已能),而是指:

1. **AI 看得见用户在干什么**——终端刚执行的命令、DB 刚查出的结果、SFTP 刚传完的文件,应成为 AI 可推理的上下文;
2. **用户看得见 AI 在干什么**——AI 经工具桥执行的 SQL/命令/传输,应实时反映到网格/终端/任务条;
3. **一句话驱动工具**——「帮我看看 web-1 的日志」→ AI 自己打开对应终端窗口并操作;
4. **跨工具编排**——一次任务横跨终端 + SFTP + DB,AI 持有任务级上下文连续操作,而不是每个面板各聊各的。

## 2. 现状架构与断点

### 2.1 已有通道(代码事实)

```
┌────────────┐  settings.update   ┌──────────────┐
│ client-nav │ ─────────────────► │ dsh host     │
│ (React 壳) │  starhub-tool-     │ (Node,内嵌    │
│            │    context 快照     │  exe,stdio)   │
└────────────┘                    └──────┬───────┘
                                         │ starhub/tool.execute
                                         │ (SDK stdio 双向 request)
                                         ▼
┌────────────┐  dsh://tool-exec   ┌──────────────┐
│ Vue 面板   │ ◄───────────────── │ Rust 主进程   │
│ (embed 窗) │  dsh://approval    │ (Tauri)       │
└────────────┘                    └──────┬───────┘
                                         │ Tauri IPC
                                         ▼
                                  ┌──────────────┐
                                  │ Go sidecar   │ (DB/ES/Redis 查询)
                                  └──────────────┘
```

- **tool-context 插件**:`agent/pre-step` 注入「当前选中工具/资产」**静态快照**(settings namespace);
- **starhub-tools 插件**:域工具 schema 在 dsh 注册,执行经 `starhub/tool.execute` 反向桥回 Rust 主进程,再分发到 owning 面板;
- **starhub-approval-bridge**(2026-08-17 由 starhub-approval 瘦身改名):preset 消费 + 风险调用升级为 ask + 确认卡桥回宿主;
- **实例操作页**:`openNewPage` 开独立 webview 窗口,开完即断联。

### 2.2 五个断点

| # | 断点 | 根因 |
|---|---|---|
| D1 | 窗口孤岛:壳会话与窗口会话互不知情 | 每个实例页独立窗口 + 独立 dsh 会话,无共享任务上下文 |
| D2 | 上下文太死:只有「选中了谁」,没有「正在发生什么」 | tool-context 是 settings 静态快照,无事件流、无活性状态 |
| D3 | AI 动作不可见:结果只回模型,不回 UI | tool-exec 的返回值只进 AI 会话文本,宿主 UI 无投影刷新 |
| D4 | 反向通道缺失:用户操作不进 AI 视野 | 面板没有任何事件上报机制 |
| D5 | 连接状态分裂:壳/窗口/AI 各自建连 | session 所有权分散在前端各面板(惰性建连),无统一注册表 |

## 3. 核心决策:收敛到哪里?

用户问:**能否都收敛到以 deepseek harness 为基础?**

### 方案 A:数据面也收敛(在 dsh/Node 里重写 SSH/SFTP/DB)

- 做法:dsh host 插件直接持有连接(Node 的 ssh2、各 DB Node 驱动),Rust `russh` 与 Go sidecar 退役。
- 判定: **不可取**。等于重写两个已通过生产验证的引擎;Node 单线程承载 xterm 高频 PTY 流与百万行查询结果是性能倒退;凭证/known_hosts/keyring 链路全部重测;违反「prefer maintained dependencies / 不要凭直觉造新架构」。

### 方案 B(推荐):控制面收敛 dsh,数据面留 Rust/Go

- **控制面**(联动总线、上下文、编排、session 注册表、意图路由)收敛为 dsh host 插件——dsh 本来就是「一切皆为插件」的 agent harness,这正是它的职责;
- **数据面**(PTY、SFTP 流、DB 查询引擎)保持 Rust/Go 不变,只加两件事:**事件上报**与**附着语义**;
- 物理通道**已经存在**:`starhub/tool.execute` 证明了 dsh host → Rust 主进程的反向 request 可行;Tauri 事件(`dsh://*` 模式)证明了 Rust → 前端广播可行;dsh 事件总线 + session log 证明了 dsh 内部沉淀上下文可行。方案 B 不发明新通道,只把三条已有通道**组合成闭环**。

**结论:可以收敛到 dsh——收敛的是「脑」(编排与上下文),不是「手」(执行引擎)。**

## 4. 目标架构(方案 B 展开)

```
                 ┌──────────────── dsh host(控制面中枢)────────────────┐
                 │  starhub-bridge      对 Rust 主进程的反向 RPC 面      │
                 │  session-registry    assetId→活跃 session 句柄注册表  │
                 │  domain-events       领域事件流(沉淀 session log)     │
                 │  live-context        pre-step 活性快照拉取与摘要注入   │
                 │  orchestrator        跨工具任务上下文 + 意图路由       │
                 └───────┬───────────────────────────────┬─────────────┘
        starhub/* RPC    │ (stdio,已有)                   │ dsh 事件/session log
                         ▼                                ▼
                 ┌────────────────┐               ┌────────────────────┐
                 │ Rust 主进程     │               │ client-nav(React 壳)│
                 │ session 所有权  │◄── 附着/投影 ──│ embed Vue 窗口       │
                 │ 事件上报        │── Tauri 事件 ─►│ (前端 = 投影+事件源) │
                 └───────┬────────┘               └────────────────────┘
                         ▼
                 ┌────────────────┐
                 │ Go sidecar     │ (查询引擎,事件经 Rust 转报)
                 └────────────────┘
```

关键不变式:**SSH/SFTP/DB session 只有 Rust/Go 一份实体**;壳内 React(需求 3)、embed Vue 窗口、AI 工具三者都按 `assetId` **附着**到同一后端 session,前端全部退化为投影。这是联动的物理基础——大家操作同一条连接,才谈得上「互相看见」。

## 5. 机制设计(六个,按依赖排序)

### M1 session 附着与注册表(治 D5,需求 3 的地基)

- Rust 主进程已有 `SshManager` / sidecar `pool.Manager`;补齐「附着」语义:`ssh_attach(assetId) → sessionId`(有则复用,无则建连),断开引用计数归零才真断;
- dsh 侧 `session-registry` 插件维护 `assetId → { sessionId, kind, attachedBy[] }` 视图,来源是 Rust 上报(不靠前端各自申报);
- 需求 3 的 root-scope store 落地时直接消费这层,天然满足「切会话不断线」。

### M2 领域事件流(治 D4)

面板/后端产生事件,统一 schema:

```jsonc
{
  "kind": "ssh.command_executed | terminal.cwd_changed | db.query_executed | db.table_opened | sftp.transfer_completed | ...",
  "assetId": "a1",
  "ts": 1724000000,
  "summary": "模型可读的单行摘要",          // 给 pre-step 注入用
  "data": { /* 领域负载,如 exitCode/rowCount/bytes */ }
}
```

- 写入点:Rust 主进程(PTY 命令回车、SFTP 完成回调)+ Go sidecar(查询完成)经 Rust 转报;
- 沉淀:经 SDK transport 写入 dsh `domain-events` 插件 → 落 session log(满足 dsh「model-visible ⟺ logged」不变式);
- 保留:环形缓冲(如每资产最近 50 条),注入时按 token 预算截断。

### M3 活性上下文 pull(治 D2)

`live-context` 插件在 `agent/pre-step` 把 M2 的静态快照升级为:**最近 N 条领域事件摘要 + 活性状态**(终端屏幕末 20 行 + cwd、DB 当前 database/打开的表/上次查询行数)。pull 经 starhub-bridge 反向调 Rust 的 `starhub/live.snapshot`,push(M2)保证不丢历史。两者互补,单一push 会在 AI 不在场时丢上下文,单一 pull 拿不到瞬态事件。

### M4 AI 动作回写(治 D3)

tool-exec 执行完成后,除返回模型文本外,由 Rust 主进程广播 `starhub://domain-event`(与 M2 同 schema,加 `origin: "ai"`):网格自动刷新、终端以高亮样式回显 AI 执行的命令、TransferDock 出现 AI 发起的传输。**AI 的手从此可见**,且因为走同一事件流,审计/回放免费获得。

### M5 意图互跳(治 D1 体验面)

- AI → 工具:新增 `starhub/open_asset`、`starhub/focus_tool` 桥方法,模型工具 `open_connection` / `focus_terminal` 落地为壳内路由切换或窗口聚焦——「帮我看看 web-1 的日志」成为现实;
- 工具 → AI:每个面板加「问 AI」入口,把当前选中的行/屏幕片段/报错文本 prefill 进壳内 AI 会话并聚焦该会话(复用 dsh session,而非新开)。

#### M5.1 open_asset / focus_tool 怎么用?——模型工具 ≠ 用户语法(答用户问)

**结论:这两个工具是模型的手,用户不需要学任何语法;`@` 是用户的嘴,两者是互补的两端。**

| 角色 | 机制 | 谁在用 | 干什么 |
|---|---|---|---|
| 用户语法 | `@` 触发(dsh 已有 `ui-input-trigger` 流水线:`/`、`@` 检测 + 候选菜单 + pick 路由,`user@host`/URL 不误触发) | 用户 | `@web-1` = 「我在说这台机器」:pick 后产生 `ReferenceInsert`,提交时翻译成模型可见引用(如 `<asset id="a1">web-1 (deploy@10.0.0.5)</asset>`),绑定资产上下文 |
| 模型工具 | `open_connection` / `focus_terminal`(starhub-tools 注册的桥接工具) | AI | 意图匹配时 AI 自行调用:打开/聚焦对应工具窗口,附着后端 session |

- **用户侧 `@` 落地方式**:StarHub 在 client-nav 注册一个 `@` source(候选来自 `get_assets` 资产列表,lexicon 即资产名清单,支持 `subscribeLexicon` 刷新);pick 只**轻绑定上下文**(assetId 进 pre-step 注入 + tool-exec 路由),**不主动打断**(不自动切窗口)——是否打开窗口由 AI 按消息意图决定调 `focus_terminal`。这样「@web-1 的密码策略是什么」这类纯问答不会被弹窗打扰。
- **完整链路示例**:用户输入「看看 @web-1 的日志」→ `@` 绑定 web-1 上下文 → AI 调 `focus_terminal(web-1)` 打开/聚焦终端窗口(M5)→ M1 附着同一后端 session → 执行命令(M4 高亮回显)→ 结果回到会话。
- **旧版 @/# 的去留**:v0.79.0 随旧 AI 内核退役的是**自研** @/# mention;本方案用的是 dsh **内核自带**的 trigger 流水线,StarHub 只贡献一个 source,不重复造轮子。

### M6 任务上下文与跨工具编排(用户优先场景)

- 一个 dsh session 即一个「任务」;`dsh_bind_session`(已有,asset 绑定)扩展为任务绑定:窗口打开时可选择「加入当前任务」;
- 编排示例 walkthrough:「把 web-1 的 /var/log 里最近的错误拉下来,清一下缓存,完事告诉我」——
  1. M5:AI 调 `focus_terminal(web-1)`(窗口聚焦/打开);
  2. M1:附着 web-1 的后端 session;M3 拉到 cwd;
  3. 执行 `grep error ...`(M4 终端高亮回显,审批走 starhub-approval-bridge);
  4. SFTP 下载结果文件(M2 记录 transfer_completed);
  5. DB 清缓存命令(同任务上下文,知道「刚才那台机器」是谁);
  6. 汇总回执——全程一个会话、一条事件流、一份审计。

## 7. 风险与开放问题

1. **事件风暴**:终端高频输出不能逐行进事件流——只记「命令回车/完成」粒度,屏幕内容走 M3 的 pull;
2. **审批疲劳**:编排链路每步都弹确认卡会不可用——需要「任务级一次批准,步进执行」的审批粒度(starhub-approval-bridge 扩展,待设计);
3. **多窗口并发写同一 session**:两个窗口同时往同一终端写命令的互斥策略(建议:后端串行化 + UI 提示「另一端正在操作」);
4. **凭证安全**:M3 拉到的事件摘要可能含敏感输出——注入模型前走现有 `memoryGuard` 同类脱敏;
5. **dsh session 与窗口生命周期**:窗口关了任务还在不在?(建议:任务在,附着断开,重开可 re-attach);
6. **命名与包归属**:新插件是进 `packages/starhub/` 还是独立 `starhub-bridge` 包;是否动 dsh 核心(本设计**不需要**动核心,全部是插件面)。
